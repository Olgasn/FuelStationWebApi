# FuelStationWebApi

[![build and test](https://github.com/Olgasn/FuelStationWebApi/actions/workflows/deployment.yml/badge.svg?branch=master)](https://github.com/Olgasn/FuelStationWebApi/actions/workflows/deployment.yml)

FuelStationWebApi — учебный демонстрационный проект, предназначенный для изучения принципов построения веб-служб и клиентских веб-приложений. В качестве предметной области выбрана работа топливной базы: проект хранит сведения о видах топлива, о емкостях для его хранения и об операциях прихода и расхода топлива. Серверная часть реализована как веб-служба REST (Representational State Transfer) на платформе ASP.NET Core. Доступ к данным защищен аутентификацией: пользователь входит в систему, получает токен доступа в формате JWT (JSON Web Token) и передает его в каждом запросе. Клиентская часть представлена страницей входа и двумя одностраничными HTML-приложениями для работы с данными; они обращаются к службе по протоколу HTTP и обмениваются с ней данными в формате JSON.

## 1. Общая характеристика проекта

Проект намеренно сохранен простым. Клиентские страницы написаны на языках HTML и JavaScript без использования каркасов для построения клиентских приложений (таких как Angular, React или Vue). Серверная часть построена на стандартных средствах ASP.NET Core и Entity Framework Core; помимо пакетов Microsoft (в том числе ASP.NET Core Identity и поддержки токенов JWT) из сторонних пакетов применяются только Swashbuckle (документирование API) и Serilog (ведение журнала). Исходный текст снабжен комментариями на русском языке, что облегчает его изучение. Для работы проекта не требуется устанавливать сервер базы данных, поскольку по умолчанию данные хранятся в файлах SQLite.

Репозиторий содержит несколько веток. Данная ветка `master` содержит полный вариант проекта: доступ к службе защищен аутентификацией на основе JWT, а сведения о пользователях хранятся в отдельной базе данных и управляются средствами ASP.NET Core Identity. Упрощенный вариант проекта, в котором аутентификация не применяется, находится в ветке `simple`.

Порядок запуска проекта описан в разделе 4, программный интерфейс службы — в разделе 8.

## 2. Цели обучения

Проект позволяет на небольшом, но законченном примере рассмотреть следующие вопросы.

- Класс `OperationsController` показывает, как средствами ASP.NET Core описываются конечные точки (endpoints) веб-службы REST, реализующие создание, чтение, изменение и удаление данных (CRUD).
- Классы каталога `Models` и класс `FuelsContext` показывают, как средствами Entity Framework Core описывается модель данных и устанавливается соответствие между классами и таблицами реляционной базы данных (подход Code First).
- Класс `DbInitializer` показывает, как при запуске приложения создается схема базы данных и выполняется ее начальное заполнение правдоподобными данными.
- Класс `OperationViewModel` показывает назначение модели представления: клиенту передается не сущность базы данных, а объект, содержащий только необходимые ему сведения, в частности названия топлива и емкости из связанных таблиц.
- Файл `Program.cs` показывает порядок настройки служб приложения (внедрение зависимостей, политика CORS, аутентификация на основе JWT, документирование API) и конвейера обработки запросов.
- Классы `AuthController` и `AuthService` показывают, как служба проверяет учетные данные и выдает токен доступа JWT, а атрибут `[Authorize]` на классе `OperationsController` — как конечные точки защищаются от анонимных обращений.
- Классы `ApplicationDbContext` и `DbUserInitializer`, а также каталог `Migrations` показывают, как средствами ASP.NET Core Identity создается и заполняется отдельная база данных пользователей и ролей.
- Страница `index.html` показывает, как клиент отправляет учетные данные, получает токен доступа и сохраняет его в хранилище `sessionStorage`.
- Страницы `fetch_operations.html` и `jq_operations.html` показывают два способа обращения к одной и той же службе из браузера (Fetch API и библиотека jQuery) с передачей токена в заголовке `Authorization` и позволяют сопоставить эти способы.
- Проект `Tests` показывает, как выполняется модульное тестирование контроллера с подменой контекста данных и как проверяется начальное заполнение на настоящей системе управления базами данных (СУБД) SQLite, размещенной в оперативной памяти.
- Файл `WebAPITest.http` показывает, как описывается набор HTTP-запросов с ожидаемыми результатами для ручной проверки службы, в том числе получения токена и обращений без него.
- Файл `.github/workflows/deployment.yml` показывает, как организуются автоматическая сборка и тестирование проекта средствами GitHub Actions.

Рекомендуемый порядок знакомства с проектом таков: классы модели (`Models`), контекст данных и начальное заполнение (`Data`), контроллеры (`Controllers`) и служба выдачи токена (`Services`), настройка приложения (`Program.cs`), клиентские страницы (`wwwroot`) и тесты (`Tests`).

| Serilog | Принимает сообщения журнала приложения и платформы ASP.NET Core, выводит их в консоль, а также записывает в текстовые файлы. |

| jQuery UI 1.14 | Предоставляет календарь для ввода даты (с русской локализацией) на обеих страницах. |

| LibMan (`Microsoft.Web.LibraryManager.Build`) | Восстанавливает клиентские библиотеки в каталог `wwwroot/lib` в соответствии с файлом `libman.json`. |
| xUnit v3, Moq, Moq.EntityFrameworkCore | Применяются в автоматических тестах: xUnit запускает тесты, Moq создает имитации объектов, а Moq.EntityFrameworkCore подменяет наборы данных контекста. |

Точные версии пакетов NuGet указаны в файлах `FuelStationWebApi/FuelStationWebApi.csproj` и `Tests/Tests.csproj`, версии клиентских библиотек — в файле `FuelStationWebApi/libman.json`. Пакет `Microsoft.Web.LibraryManager.Build` восстанавливает клиентские библиотеки при сборке проекта, но не удаляет файлы прежних версий. Поэтому после изменения версий следует удалить устаревшие файлы из каталога `wwwroot/lib` и проверить пути подключения библиотек в HTML-страницах. Версия jQuery UI должна соответствовать основной версии jQuery: для jQuery 4 применяется jQuery UI 1.14.

## 4. Запуск проекта

### Требования к окружению

Для запуска проекта необходимы пакет SDK для .NET версии 10.0 (установленную версию можно проверить командой `dotnet --version`), система контроля версий Git и веб-браузер. При первой сборке для загрузки пакетов NuGet и клиентских библиотек может потребоваться доступ к сети Интернет.

### Запуск из командной строки

Для запуска службы следует выполнить следующие команды:

```text
git clone https://github.com/Olgasn/FuelStationWebApi
cd FuelStationWebApi/FuelStationWebApi
dotnet run
```

Первая команда создает копию репозитория (клонируется ветка по умолчанию — `master`) в каталоге, имя которого совпадает с именем репозитория. Вторая команда выполняет переход в каталог проекта веб-службы, который расположен внутри каталога репозитория и имеет то же имя. Третья команда выполняет сборку и запуск службы. Остановить службу можно сочетанием клавиш Ctrl+C.

### Запуск из среды разработки

Решение `FuelStationWebApi.sln` можно открыть в версии Visual Studio, поддерживающей .NET 10, выбрать профиль запуска `FuelStationWebApi` и запустить проект. Профиль настроен так, что при запуске в браузере открывается страница Swagger UI (параметр `launchUrl` в файле `Properties/launchSettings.json`).

В Visual Studio Code достаточно открыть каталог репозитория и выполнить команду `dotnet run` в каталоге проекта веб-службы во встроенном терминале. Для запуска с отладкой предусмотрена конфигурация «.NET Core Launch (web)». Она находится в файле `.vscode/launch.json` (для случая, когда открыт каталог репозитория) и в файле `FuelStationWebApi/.vscode/launch.json` (для случая, когда открыт каталог проекта). Конфигурация предварительно собирает проект, запускает сборку `bin/Debug/net10.0/FuelStationWebApi.dll` и открывает в браузере страницу Swagger UI, как только служба сообщает адрес, по которому она принимает запросы.

### Адреса службы и клиентов

После запуска с профилем по умолчанию служба принимает запросы по адресу `http://localhost:57126`. В браузере доступны следующие адреса.

| Адрес | Назначение |
| --- | --- |
| `http://localhost:57126/` и `http://localhost:57126/index.html` | Открывают страницу входа, на которой выдается токен доступа. |
| `http://localhost:57126/swagger/index.html` | Открывает интерактивную документацию API (Swagger UI), в которой запросы можно выполнять непосредственно из браузера. |
| `http://localhost:57126/fetch_operations.html` | Открывает клиент, использующий Fetch API; перед его использованием необходимо выполнить вход. |
| `http://localhost:57126/jq_operations.html` | Открывает клиент, использующий jQuery; перед его использованием необходимо выполнить вход. |
| `http://localhost:57126/api/operations` | Возвращает список операций в формате JSON; без токена доступа служба отвечает кодом 401. |

Запрос к адресу `http://localhost:57126/` открывает страницу входа `index.html`: компонент `UseDefaultFiles` подставляет ее вместо отсутствующего имени файла. Чтобы начать работу, на странице входа нужно нажать кнопку «Логин» (учетные данные администратора заполнены заранее, см. раздел 8) и выбрать один из клиентов. Адрес и порт службы задаются профилями запуска в файле `Properties/launchSettings.json` (профиль `FuelStationWebApi` использует порт 57126, профиль `IIS Express` — порт 57125). Их можно изменить параметром командной строки `--urls`, например: `dotnet run --urls http://localhost:5000`. При размещении службы на другом узле или порту в приведенных адресах следует заменить `localhost:57126` соответствующими значениями.

## 6. Предметная область и модель данных

Топливная база хранит топливо в емкостях различных типов: резервуарах, цистернах, бочках и других. Движение топлива регистрируется операциями: приход увеличивает остаток топлива в емкости, а расход уменьшает его. Модель данных состоит из трех сущностей, которым соответствуют таблицы `Fuels`, `Tanks` и `Operations`. Связи между ними показаны на следующей схеме.

```text
Fuel (1) ---- (N) Operation (N) ---- (1) Tank
```

Каждая операция относится ровно к одному виду топлива и ровно к одной емкости, а к одному виду топлива или к одной емкости может относиться любое число операций. Прямой связи между топливом и емкостью в схеме базы данных нет: они связываются только через операции. Остаток топлива в емкости в базе данных не хранится; его можно вычислить как сумму величин всех операций по этой емкости.

### Сущность Fuel (вид топлива)

| Поле | Тип | Описание |
| --- | --- | --- |
| `FuelID` | `int` | Является первичным ключом записи. |
| `FuelType` | `string` | Содержит название вида топлива. |
| `FuelDensity` | `float` | Содержит плотность топлива. |
| `Operations` | `ICollection<Operation>` | Ссылается на операции с данным видом топлива. |

### Сущность Tank (емкость)

| Поле | Тип | Описание |
| --- | --- | --- |
| `TankID` | `int` | Является первичным ключом записи. |
| `TankType` | `string` | Содержит тип (название) емкости; в начальных данных к нему добавлен порядковый номер емкости. |
| `TankWeight` | `float` | Содержит массу пустой емкости. |
| `TankVolume` | `float` | Содержит объем емкости. |
| `TankMaterial` | `string` | Содержит материал, из которого изготовлена емкость. |
| `TankPicture` | `string` | Предназначено для ссылки на файл с изображением емкости; в начальных данных и на клиентских страницах не используется. |
| `Operations` | `ICollection<Operation>` | Ссылается на операции с данной емкостью. |

### Сущность Operation (операция)

| Поле | Тип | Описание |
| --- | --- | --- |
| `OperationID` | `int` | Является первичным ключом записи. |
| `FuelID` | `int` | Является внешним ключом, ссылающимся на вид топлива. |
| `TankID` | `int` | Является внешним ключом, ссылающимся на емкость. |
| `Inc_Exp` | `float?` | Содержит величину операции: положительное число означает приход, отрицательное число — расход; значение может отсутствовать. |
| `Date` | `DateTime` | Содержит дату операции. |
| `Fuel`, `Tank` | `Fuel`, `Tank` | Являются навигационными свойствами, ссылающимися на связанные записи. |

В начальных данных приняты следующие единицы измерения: объем емкости и величина операции выражаются в литрах, масса емкости — в килограммах, плотность топлива — в килограммах на литр. Сама схема базы данных единицы измерения не фиксирует.

Сведения о пользователях в эту схему не входят: они хранятся в отдельной базе данных `users.db` в таблицах Identity (`AspNetUsers`, `AspNetRoles`, `AspNetUserRoles` и других) и с таблицами топливной базы не связаны.

## 7. Архитектура серверной части

Серверная часть построена по классической схеме: запрос клиента проходит через конвейер обработки запросов ASP.NET Core, попадает в контроллер, а контроллер обращается к базе данных через контекст Entity Framework Core.

```text
Браузер (HTML-страница и JavaScript)
    |   HTTP-запрос с заголовком Authorization: Bearer <токен>;
    |   данные запроса и ответа передаются в формате JSON
    v
Конвейер обработки запросов ASP.NET Core (Program.cs)
    |   статические файлы, маршрутизация, CORS,
    |   проверка токена (аутентификация и авторизация), выбор конечной точки
    v
AuthController (вход) и OperationsController (данные) (Controllers)
    |   проверка пароля и выдача токена / запросы LINQ к наборам данных контекста
    v
UserManager (Identity)            FuelsContext (Entity Framework Core)
    |   SQL-запросы                   |   SQL-запросы
    v                                 v
База данных SQLite                База данных SQLite
(файл users.db)                   (файл fuels.db)
```

Настройка приложения выполняется в файле `Program.cs` в следующем порядке.

1. Настраивается запись журнала с помощью Serilog: сообщения выводятся в консоль и записываются в текстовый файл `FuelStationWebApiLog-<дата>.txt`, причем для каждых суток создается новый файл. Файлы журнала создаются в рабочем каталоге приложения и исключены из системы контроля версий правилом в файле `.gitignore`. Затем Serilog подключается к узлу приложения вызовом `UseSerilog`, поэтому в журнал попадают и сообщения самой платформы ASP.NET Core уровня Information и выше, в частности сведения о запросах и тексты SQL-запросов, которые формирует Entity Framework Core. Стандартные поставщики журнала при этом заменяются, поэтому уровни сообщений задаются в `Program.cs`, а раздел `Logging` при использовании Serilog не действовал бы и потому удален из файла `appsettings.json`.
2. Регистрируются службы приложения: контекст данных `FuelsContext` с поставщиком SQLite; контекст `ApplicationDbContext` и средства Identity (`AddIdentity`) для базы данных пользователей, строка подключения которой называется `IdentityConnection`; аутентификация по схеме JWT Bearer (`AddAuthentication` и `AddJwtBearer`) с параметрами проверки токена из раздела `JwtSettings` файла `appsettings.json`; служба `AuthService`; политика CORS `AllowAll`; контроллеры и генератор описания API Swagger, дополненный описанием схемы Bearer.
3. Задается конвейер обработки запросов. Компоненты Swagger обслуживают адреса, начинающиеся с `/swagger`. Страница сведений об исключениях выводит подробное описание необработанных ошибок. Компоненты `UseDefaultFiles` и `UseStaticFiles` отдают содержимое каталога `wwwroot`, причем адрес `/` сопоставляется со страницей `index.html`. Затем выполняется маршрутизация, применяется политика CORS, компонент аутентификации проверяет токен из заголовка `Authorization`, компонент авторизации применяет атрибуты `[Authorize]`, и запрос передается контроллеру. Swagger и статические файлы обслуживаются до проверки токена, поэтому доступны без входа.
4. Перед началом приема запросов вызываются методы `DbUserInitializer.Initialize` (роли и учетная запись администратора в базе данных пользователей) и `DbInitializer.Initialize` (создание и заполнение базы данных топливной базы); подробнее об этом сказано в разделе 10. Метод `DbUserInitializer.Initialize` асинхронный, а метод `Main` нет, поэтому при запуске его завершение ожидается синхронно (`GetAwaiter().GetResult()`). Исключение, возникшее при инициализации одной из баз, не прерывает запуск службы, а записывается в журнал.

Контекст `FuelsContext` регистрируется методом `AddDbContext` и передается в конструктор контроллера механизмом внедрения зависимостей. Благодаря этому контроллер не создает контекст самостоятельно, а при тестировании вместо него может быть подставлена имитация. Класс `FuelsContext` содержит наборы данных `Fuels`, `Tanks` и `Operations`. Эти свойства объявлены виртуальными, а у класса имеется конструктор без параметров, что позволяет подменять контекст имитацией в модульных тестах.

Для списков операций контроллер формирует объекты `OperationViewModel`, в которые вместе с данными операции включаются названия топлива (`FuelType`) и емкости (`TankType`) из связанных таблиц. Справочники топлива и емкостей, а также отдельная операция возвращаются без такого преобразования, то есть в виде сущностей.

## 8. Программный интерфейс

Конечные точки работы с данными реализованы в контроллере `OperationsController`, а конечная точка входа — в контроллере `AuthController`. Маршрут контроллера `OperationsController` задан атрибутом `[Route("api/[controller]")]` и имеет вид `/api/operations`; регистр букв в адресе не учитывается, а в документации Swagger адрес показан как `/api/Operations`. Все его конечные точки защищены атрибутом `[Authorize]`: запрос должен содержать заголовок `Authorization: Bearer <токен>`, иначе служба отвечает кодом 401. Токен выдает конечная точка входа (подраздел «Аутентификация» ниже). Данные запросов и ответов передаются в формате JSON. Имена свойств начинаются со строчной буквы (например, `operationID`, `inc_Exp`), а даты записываются в формате ISO 8601 (например, `2026-11-26T00:00:00`).

| Метод | Адрес | Назначение |
| --- | --- | --- |
| `POST` | `/api/auth` | Выполняет вход: принимает в теле запроса адрес электронной почты и пароль и возвращает токен доступа. Токен для самого запроса входа не нужен; все остальные запросы таблицы требуют токен. |
| `GET` | `/api/operations` | Возвращает список всех операций; для каждой операции указаны названия топлива и емкости. |
| `GET` | `/api/operations/FilteredOperations?FuelID={код}&TankID={код}` | Возвращает операции, удовлетворяющие условиям фильтра. Параметры необязательны: отсутствующее, нечисловое или не превышающее нуля значение означает, что условие по соответствующему полю не применяется. Если заданы оба условия, должны выполняться оба. |
| `GET` | `/api/operations/fuels` | Возвращает справочник видов топлива. |
| `GET` | `/api/operations/tanks` | Возвращает справочник емкостей. |
| `GET` | `/api/operations/{id}` | Возвращает одну операцию по ее коду. В ответ включаются коды топлива и емкости, но не их названия. |
| `POST` | `/api/operations` | Регистрирует новую операцию. Объект `Operation` передается в теле запроса, а код операции присваивает база данных. |
| `PUT` | `/api/operations` | Изменяет существующую операцию. Объект `Operation` передается в теле запроса вместе с кодом операции, в адресе код не указывается. |
| `DELETE` | `/api/operations/{id}` | Удаляет операцию с указанным кодом. |

При успешном выполнении запроса служба возвращает код 200 и JSON-представление результата. Методы `POST`, `PUT` и `DELETE` возвращают соответственно созданную, измененную или удаленную операцию. Ошибки обозначаются следующими кодами.

- Код 400 возвращается, если тело запроса `POST` или `PUT` пусто либо содержит некорректный JSON или недопустимые значения полей.
- Код 401 возвращается, если в запросе к `/api/operations` нет заголовка `Authorization`, схема отличается от `Bearer`, токен некорректен, подписан другим ключом или просрочен, а в запросе `POST /api/auth` — если пользователь не найден или пароль неверен. Проверка токена выполняется раньше привязки тела запроса и проверок контроллера, поэтому запрос без токена к существующей конечной точке получает код 401 независимо от своего содержимого; несуществующий адрес и неподдерживаемый метод по-прежнему дают коды 404 и 405.
- Код 404 возвращается, если операция с указанным кодом не найдена; для запроса `PUT` этот код возвращается и в том случае, когда код операции в теле запроса не указан.
- Код 405 возвращается, если использован метод HTTP, не предусмотренный для данного адреса, например `PUT` с кодом в адресе или `DELETE` без кода.
- Код 415 возвращается, если тело запроса `POST` или `PUT` передано с типом содержимого, отличным от `application/json`.
- Код 500 возвращается, если в запросе `POST` или `PUT` указан несуществующий код топлива или емкости. Ссылочную целостность проверяет база данных, а не контроллер. Код 500 возвращает и запрос `POST /api/auth` с пустым телом или без адреса электронной почты: контроллер входа тело запроса не проверяет.

### Аутентификация

Вход выполняет запрос `POST /api/auth`. В теле запроса передаются адрес электронной почты и пароль (поля `email` и `password`):

```json
{
  "email": "admin@gmail.com",
  "password": "_Aa123456"
}
```

Служба ищет пользователя средствами ASP.NET Core Identity и проверяет пароль. Если проверка прошла успешно, служба возвращает код 200 и токен JWT, иначе — код 401. Чтобы токен пришел в виде JSON-строки (в кавычках), запрос должен содержать заголовок `Accept: application/json`; без него служба вернет тот же токен как простой текст (`text/plain`) без кавычек. Клиентские страницы этот заголовок передают.

Токен состоит из трех частей, разделенных точками: заголовка, полезной нагрузки и подписи. В полезной нагрузке содержатся имя пользователя (`sub`), уникальный идентификатор токена (`jti`), идентификатор пользователя, издатель (`iss`), получатель (`aud`) и срок действия (`exp`). Подпись формируется по алгоритму HMAC-SHA256 с ключом из раздела `JwtSettings` файла `appsettings.json`. Токен действует 30 минут. При каждом запросе к защищенной конечной точке служба проверяет подпись, издателя, получателя и срок действия (параметры `TokenValidationParameters` в `Program.cs`), а клиент передает токен в заголовке `Authorization: Bearer <токен>`.

Учетная запись администратора (`admin@gmail.com`, пароль `_Aa123456`) и роли `admin` и `user` уже есть в файле `users.db`; при начальном заполнении (раздел 10) они создаются заново, только если отсутствуют. Регистрации новых пользователей в службе нет. Роли в проекте не применяются: атрибут `[Authorize]` не указывает роль, поэтому запросы к `/api/operations` разрешены любому пользователю с действительным токеном.

Интерактивная документация API (Swagger UI) доступна по адресу `/swagger/index.html`, а описание в формате OpenAPI — по адресу `/swagger/v1/swagger.json`. Чтобы выполнять защищенные запросы из Swagger UI, необходимо получить токен запросом `POST /api/auth`, нажать кнопку Authorize и ввести токен (без кавычек): он будет подставляться во все запросы. Описания методов и параметров формируются из XML-комментариев (теги `summary`, `remarks`, `param`, `returns`), записанных в тексте контроллера. Создание файла документации включено в `FuelStationWebApi.csproj` параметром `GenerateDocumentationFile`, а подключение этого файла выполняется в `Program.cs` вызовом `IncludeXmlComments`.

## 9. Клиентская часть

Клиентская часть состоит из страницы входа `index.html` и двух самостоятельных страниц для работы с данными, расположенных в каталоге `wwwroot`. Страница `fetch_operations.html` обращается к службе средствами Fetch API, а страница `jq_operations.html` — средствами библиотеки jQuery. Обе страницы выполняют одни и те же действия, поэтому их целесообразно сопоставлять. Оформление страниц задает Bootstrap 5, а календарь для ввода даты в формате «ГГГГ-ММ-ДД» (с русской локализацией) предоставляет jQuery UI. В заголовке страниц выводится логотип топливной базы (`img/logo.svg`), который одновременно служит значком вкладки браузера. Справа от логотипа на страницах данных расположена кнопка «Войти», которая ведет на страницу входа.

### Вход в систему

Страница `index.html` содержит форму входа, в которой заранее заполнены учетные данные администратора. После нажатия кнопки «Логин» страница отправляет запрос `POST /api/auth` с заголовком `Accept: application/json`, получает токен, сохраняет его в хранилище `sessionStorage` браузера под ключом `accessToken`, выводит имя пользователя (поле `sub` полезной нагрузки токена, которую страница декодирует функцией `atob`) и показывает ссылки на страницы данных. Кнопка «Выйти» удаляет токен из хранилища. Хранилище `sessionStorage` привязано к вкладке браузера и очищается при ее закрытии, поэтому после закрытия вкладки вход необходимо выполнить заново.

Страницы данных читают токен из хранилища при загрузке и передают его в заголовке `Authorization` каждого запроса к службе. Если токена нет или срок его действия истек, служба отвечает кодом 401; страницы этот ответ не обрабатывают, поэтому таблица и выпадающие списки остаются пустыми, и необходимо снова выполнить вход.

### Возможности страниц

1. Просмотр данных начинается при открытии страницы: загружаются все операции, а также справочники топлива и емкостей, из которых формируются выпадающие списки формы. Операции выводятся в таблице по 10 строк на странице. Под таблицей расположены панель переключения страниц (кнопки перехода к первой, предыдущей, следующей и последней страницам и не более пяти номеров страниц вокруг текущей) и сведения о номере текущей страницы и общем числе операций.
2. Фильтрация выполняется по виду топлива и (или) емкости: пользователь выбирает нужные значения и нажимает кнопку «Загрузить». Страница запрашивает у службы отфильтрованный список и показывает его первую страницу. Пункт «(выбор)» означает, что условие по соответствующему полю не задано.
3. Добавление операции выполняется с помощью формы: пользователь выбирает топливо и емкость, вводит величину прихода (положительное число) или расхода (отрицательное число), выбирает дату и нажимает кнопку «Сохранить». Новая операция добавляется в конец списка, после чего открывается последняя страница таблицы.
4. Изменение операции начинается со ссылки «Изменить» в строке таблицы: она переносит данные операции в форму, а надпись над формой меняется на «Изменить:». После нажатия кнопки «Сохранить» изменения отправляются службе, а строка таблицы обновляется.
5. Удаление операции выполняется ссылкой «Удалить» в строке таблицы.
6. Сброс формы выполняется кнопкой «Сбросить»: она очищает форму и возвращает ее в режим добавления.

Постраничный вывод выполняется на стороне клиента: служба возвращает все операции сразу, а страница показывает их частями. При этом программный интерфейс службы остается неизменным.

### Допущение клиентов о кодах записей

Клиентские страницы используют номер выбранного пункта выпадающего списка (свойство `selectedIndex`) в качестве кода топлива или емкости. Первый пункт списка «(выбор)» имеет номер 0, а записи справочника следуют за ним. Поэтому запись справочника с кодом N должна находиться в списке на позиции N: коды должны идти подряд, начиная с единицы, в том же порядке, в котором служба возвращает записи. Начальное заполнение базы данных это условие выполняет, но при ручном изменении справочников оно может нарушиться. Атрибут `value` пунктов списка тоже содержит код записи, однако клиентские страницы его не используют.

### Сопоставление двух реализаций

| Особенность | `fetch_operations.html` | `jq_operations.html` |
| --- | --- | --- |
| Обращение к службе | Применяются функция `fetch` и конструкция `async/await`. | Применяется метод `$.ajax` с функциями обратного вызова. |
| Передача токена | Объект `headers` в параметрах функции `fetch`. | Параметр `headers` метода `$.ajax`. |
| Формирование строк таблицы | Элементы страницы создаются средствами DOM (`createElement`, `append`). | Строка разметки HTML собирается конкатенацией и вставляется методом `html()`. |
| Обработка событий | Обработчик назначается каждому созданному элементу методом `addEventListener`. | Общие обработчики делегируются элементу `body`, например `$("body").on("click", ".editLink", ...)`. |
| Роль библиотеки jQuery | Библиотека подключена только потому, что от нее зависит календарь jQuery UI. | Библиотека используется для обращений к службе, работы со страницей и календаря. |

## 10. Хранение данных и начальное заполнение

### Файл базы данных

По умолчанию используются две базы данных SQLite: данные топливной базы хранятся в файле `fuels.db`, а сведения о пользователях и ролях — в файле `users.db`. Пути к файлам задаются строками подключения `FuelSqlite` и `IdentityConnection` в файле `appsettings.json` (`DataSource=fuels.db` и `DataSource=users.db`) и отсчитываются от рабочего каталога приложения. При запуске командой `dotnet run` из каталога проекта используются файлы `FuelStationWebApi/fuels.db` и `FuelStationWebApi/users.db`, находящиеся в репозитории. Строки подключения не содержат разделителей пути, поэтому не зависят от операционной системы.

Изменения, выполняемые через API, записываются непосредственно в этот файл и поэтому отражаются в системе контроля версий как изменение двоичного файла. При запуске собранного приложения из каталога `bin` используются копии файлов: копия `fuels.db` заменяется при каждой сборке, а копия `users.db` — только если исходный файл новее (значения `Always` и `PreserveNewest` параметра `CopyToOutputDirectory` в `FuelStationWebApi.csproj`). Служебные файлы `users.db-shm` и `users.db-wal` могут изменяться при работе службы.

### Создание схемы

Схема базы данных топливной базы создается методом `Database.EnsureCreated()` при начальном заполнении, если базы данных еще нет. Миграции Entity Framework Core для нее не используются, поэтому изменение классов модели не приводит к изменению существующего файла базы данных: для применения новой структуры файл необходимо создать заново.

Схема базы данных пользователей, напротив, создается миграцией `Migrations/20241109121640_InitialSeedUsers` (таблицы Identity), а метод `EnsureCreated` для нее не вызывается. Файл `users.db` из репозитория уже содержит схему и учетную запись администратора. Если файла нет, служба создаст пустой файл без таблиц: при запуске в журнал будет записана ошибка (причина — «no such table»), служба продолжит работу, но запрос входа будет завершаться ответом с кодом 500, и получить токен будет нельзя. Чтобы создать схему, следует выполнить в каталоге проекта команду `dotnet tool restore`, а затем `dotnet ef database update --context ApplicationDbContext`.

### Начальное заполнение

Начальное заполнение обеих баз данных выполняется один раз при запуске службы, до начала приема запросов: `Program.cs` вызывает сначала `DbUserInitializer.Initialize`, а затем `DbInitializer.Initialize`. Сбой заполнения одной из баз не прерывает запуск службы и не мешает заполнению другой: ошибка записывается в журнал.

Класс `DbUserInitializer` создает роли `admin` и `user`, если их нет, а также учетную запись администратора с адресом `admin@gmail.com` и паролем `_Aa123456`, которой назначается роль `admin`. Эти сведения записаны в тексте класса и заранее подставлены в форму входа, что допустимо только в учебном проекте.

Класс `DbInitializer` заполняет таблицы топливной базы, только если таблица видов топлива пуста; в остальных случаях база данных остается без изменений. Заполнение выполняется одним вызовом `SaveChanges`, то есть в одной транзакции, поэтому база данных не может оказаться заполненной частично. Данные имитируют работу топливной базы.

В таблицу видов топлива заносятся 14 записей: три марки бензина (Аи-92, Аи-95, Аи-98), три марки дизельного топлива (летнее, зимнее и арктическое), два вида керосина (авиационный ТС-1 и осветительный КО-25), два вида мазута (М-40 и М-100), бытовое печное топливо, нефть Urals, топливный этанол и пропан-бутан. Для каждого вида указана плотность.

В таблицу емкостей заносятся 35 записей: вертикальные (РВС) и горизонтальные (РГС) стальные резервуары, газгольдеры, автоцистерны, железнодорожные цистерны, еврокуб, бочки и канистра. Объем емкостей составляет от 20 л до 1 000 000 л. В названии каждой емкости указан ее порядковый номер (например, «РВС-700 №3»). Каждая емкость хранит один вид топлива, при этом один вид топлива может храниться в нескольких емкостях.

В таблицу операций заносятся 300 записей. Операции моделируют работу базы следующим образом.

- В начале периода все емкости пусты, поэтому первая операция по каждой емкости является ее начальным заполнением.
- Если остаток топлива в емкости не превышает 25 % ее объема, емкость пополняется до 85–95 % объема (приход). При остатке до 70 % объема пополнение также возможно, но происходит редко (с вероятностью 15 %).
- В остальных случаях из емкости отпускается топливо порциями по 5–25 % ее объема (расход).
- Величина операции округляется до десятков литров для емкостей объемом от 1000 л и до целых литров для остальных.
- Дата операции — случайные сутки из последних 90, не считая текущих. Операции создаются в хронологическом порядке, поэтому код операции растет вместе с ее датой.

Благодаря такому правилу остаток топлива в любой емкости никогда не бывает отрицательным и не превышает ее объема. Генератор псевдослучайных чисел инициализируется постоянным значением, поэтому при каждом создании базы данных формируется один и тот же набор записей; от дня создания зависят только даты операций.

От начальных данных зависят и другие части проекта: клиентские страницы (последовательные коды справочников), файл `WebAPITest.http` (коды топлива 2 и 3, коды емкостей 5 и 24, количества записей) и тесты в файле `Tests/DbInitializerTest.cs`. Поэтому при изменении класса `DbInitializer` необходимо согласованно обновить перечисленные файлы. Кроме того, существующий файл `fuels.db` повторно не заполняется, и его необходимо заменить.

### Возврат к исходному состоянию

Чтобы вернуть базу данных к исходному состоянию после экспериментов, следует остановить службу и восстановить файл из репозитория командой `git restore FuelStationWebApi/fuels.db` (для базы данных пользователей — `git restore FuelStationWebApi/users.db`), выполненной в корневом каталоге репозитория. Если удалить файл `fuels.db`, то при следующем запуске служба создаст новую базу данных и заполнит ее заново. Файл `users.db` удалять не следует: схему в нем создают только миграции (см. выше). В этом случае даты операций будут отсчитываться от дня создания, а рядом с файлом могут появиться служебные файлы SQLite `fuels.db-wal` и `fuels.db-shm`.

Если начальное заполнение завершилось ошибкой, служба продолжает работу, а сообщение об ошибке («An error occurred while users db initialization» или «An error occurred while fuels db initialization») выводится в консоль и записывается в файл журнала `FuelStationWebApiLog-<дата>.txt` в рабочем каталоге. Повторно заполнение выполняется только при следующем запуске. Признаками такой ситуации служат пустые таблицы топливной базы и ответ с кодом 500 на запрос входа. Типичные причины — отсутствие схемы в файле `users.db` и недоступность файлов баз данных.

### Использование другой СУБД

В файле `Program.cs`, помимо действующего варианта для SQLite, в виде комментариев приведены варианты подключения к SQL Server (локальному и удаленному) и к MySQL. Соответствующие строки подключения находятся в файле `appsettings.json` под именами `DefaultConnection` (локальный экземпляр LocalDB), `RemoteSQLConnection` (удаленный SQL Server) и `FuelConnectionMysql` (MySQL). Эти варианты относятся только к базе данных топливной базы (`FuelsContext`); база данных пользователей по-прежнему хранится в SQLite.

Чтобы воспользоваться вариантом SQL Server, необходимо выполнить следующие действия.

1. Подключить к проекту пакет `Microsoft.EntityFrameworkCore.SqlServer`.
2. Добавить в файл `Program.cs` директиву `using Microsoft.Data.SqlClient;`.
3. Раскомментировать нужный вариант подключения и закомментировать регистрацию контекста для SQLite, так как в приложении должен быть зарегистрирован один поставщик данных.

Для варианта MySQL аналогичным образом требуется пакет соответствующего поставщика данных Entity Framework Core.

Строка подключения `RemoteSQLConnection` не содержит учетных данных. Имя пользователя и пароль для доступа к удаленному SQL Server считываются из хранилища секретов пользователя (User Secrets) и подставляются в строку подключения. Структура файла `secrets.json`, в котором хранятся эти данные, следующая.

```json
{
  "Database:login": "",
  "Database:password": ""
}
```

В файле необходимо указать имя пользователя и пароль для доступа к базе данных, размещенной на удаленном SQL Server. Значения можно задать командами `dotnet user-secrets set "Database:login" "имя_пользователя"` и `dotnet user-secrets set "Database:password" "пароль"`, выполненными в каталоге проекта. Файл `secrets.json` при этом создается вне репозитория (в Windows — по пути `%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json`, в Linux и macOS — по пути `~/.microsoft/usersecrets/<UserSecretsId>/secrets.json`), поэтому учетные данные не попадают в систему контроля версий. Идентификатор `UserSecretsId` задан в файле `FuelStationWebApi.csproj`.

## 11. Тестирование

### Автоматические тесты

Автоматические тесты расположены в проекте `Tests` и написаны с использованием xUnit. Для их запуска достаточно выполнить в корневом каталоге репозитория команду `dotnet test`: будут собраны оба проекта решения и выполнены все тесты.

- Класс `OperationsControllerTest` содержит модульные тесты контроллера. Контекст данных заменяется имитацией (Mock) библиотеки Moq, а наборы данных подменяются средствами Moq.EntityFrameworkCore, поэтому база данных не используется. Тесты проверяют получение списков и справочников, преобразование операции в модель представления, все варианты фильтрации, получение операции по коду, а также результаты (`OkObjectResult`, `NotFoundResult`, `BadRequestResult`) и число вызовов `SaveChanges` при добавлении, изменении и удалении. Поскольку запросы выполняются над коллекциями в памяти, особенности преобразования запросов в SQL такими тестами не проверяются. Контроллер создается и вызывается напрямую, без конвейера ASP.NET Core, поэтому атрибут `[Authorize]` и проверка токена такими тестами не проверяются. Автоматических тестов для `AuthController`, `AuthService` и защиты конечных точек нет: их проверяют запросы раздела 0 файла `WebAPITest.http`.
- Класс `DbInitializerTest` содержит тесты начального заполнения. Используется настоящая СУБД SQLite, но размещенная в оперативной памяти, поэтому файл `fuels.db` тесты не затрагивают. Тесты проверяют число записей в таблицах, непрерывность кодов начиная с единицы, наличие операций для пар «топливо — емкость», указанных в `WebAPITest.http`, осмысленность названий и параметров, хранение в каждой емкости одного вида топлива, нахождение остатка топлива в пределах от нуля до объема емкости, хронологический порядок и период дат, а также неизменность данных при повторном запуске инициализации. Эти тесты намеренно закрепляют начальные данные, поскольку от них зависят другие части проекта (см. раздел 10).
- Класс `TestDataHelper` формирует небольшие наборы тестовых данных для тестов контроллера.

### Ручная проверка

Файл `FuelStationWebApi/WebAPITest.http` содержит запросы ко всем конечным точкам, а также к входу, случаям обработки ошибок (неверные учетные данные, обращение без токена, некорректные данные, несуществующие записи, неподдерживаемые методы), политике CORS, Swagger и статическим файлам. Перед каждым запросом в комментарии указан ожидаемый результат (код ответа и содержимое), зафиксированный при работе приложения. Файл можно выполнять в актуальной версии Visual Studio 2022 либо в Visual Studio Code с расширением REST Client.

Перед выполнением запросов необходимо запустить службу. Первым следует отправить запрос `login` из раздела 0: он получает токен доступа, который переменная `token` подставляет в заголовок `Authorization` остальных запросов. Через 30 минут токен истекает, и запрос `login` нужно отправить повторно; если клиент не поддерживает ссылку на ответ другого запроса в переменной, токен можно подставить вручную. Запросы следует отправлять сверху вниз: запросы, создающие записи, имеют имена, а последующие запросы ссылаются на их ответы. Созданные в ходе проверки записи удаляются запросами из раздела 7 файла. Ожидаемые результаты основаны на начальных данных, поэтому при изменении этих данных файл необходимо обновлять.

### Непрерывная интеграция

Рабочий процесс GitHub Actions `build and test` описан в файле `.github/workflows/deployment.yml`. Он запускается при каждой передаче изменений в репозиторий (push), а также при запросах на слияние (pull request) в ветку `master`, если изменены файлы `.cs` или `.csproj`. Процесс выполняется в операционных системах Ubuntu, Windows и macOS с пакетом SDK для .NET версии 10.0.x и включает восстановление зависимостей, сборку в конфигурации Release и запуск тестов. Значок состояния в начале настоящего документа показывает результат последнего запуска для ветки `master`.

## 12. Принятые упрощения и ограничения

Проект предназначен для обучения, поэтому ряд решений намеренно упрощен. Эти решения не следует переносить в промышленные системы без доработки.

- Аутентификация упрощена. Токен нельзя отозвать: кнопка «Выйти» лишь удаляет его на стороне клиента, а сам токен остается действительным до истечения срока (30 минут). Токен хранится в `sessionStorage`, доступном любому сценарию страницы, поэтому уязвимость межсайтового выполнения сценариев (XSS) приводит к его краже. Служба не ограничивает число неудачных попыток входа.
- Секреты находятся в репозитории: ключ подписи токена записан в файле `appsettings.json`, а имя и пароль администратора — в классе `DbUserInitializer` и на странице `index.html`. В реальных приложениях ключ хранят в защищенном хранилище (переменные окружения, User Secrets, специализированные службы), а пароли по умолчанию не применяют.
- Параметр `RequireHttpsMetadata` отключен, а в примерах служба работает по протоколу HTTP, поэтому пароль и токен передаются по сети в открытом виде. В реальных приложениях необходим HTTPS.
- Авторизация не различает пользователей: роли `admin` и `user` создаются, но не применяются, и любой пользователь с действительным токеном может выполнять любые операции. Регистрации новых пользователей в службе нет.
- Контроллер входа не проверяет тело запроса: пустое тело или отсутствие адреса электронной почты приводят к необработанному исключению и ответу с кодом 500.
- Политика CORS `AllowAll` разрешает запросы с любых источников, любыми методами и заголовками. В реальных приложениях список разрешенных источников необходимо ограничивать.
- Страница сведений об исключениях включена независимо от среды выполнения, поэтому при ошибке клиент получает подробные технические сведения. Для промышленной эксплуатации такая настройка недопустима.
- Контроллер лишь проверяет, что тело запроса не пусто, а остальные входные данные не проверяет. Несуществующие коды топлива и емкости обнаруживает база данных, и это приводит к ответу с кодом 500. Контроллер также не проверяет, что остаток топлива в емкости остается неотрицательным и не превышает ее объема; начальные данные эти условия соблюдают, а запросы к службе — нет.
- Ответ на создание операции имеет код 200, а не 201 (Created). Изменение операции выполняется методом `PUT` с передачей кода в теле запроса, а не в адресе.
- Методы контроллера синхронные. Это упрощает код, однако в промышленных службах обращения к базе данных обычно выполняют асинхронно.
- Через API можно изменять только операции. Справочники топлива и емкостей доступны для чтения и заполняются при начальной инициализации.
- Служба возвращает все операции без постраничного разбиения, которое выполняется на стороне клиента. При большом числе записей такой подход неэффективен.
- Клиентские страницы принимают номер выбранного пункта списка за код записи справочника (см. раздел 9).
- Выпадающие списки на обеих страницах, а на странице с jQuery и строки таблицы формируются конкатенацией строк разметки без экранирования значений. Это допустимо лишь потому, что названия берутся из справочников, которые через API не изменяются. В реальных приложениях значения необходимо экранировать или вставлять в страницу как текст.
- Обработка ошибок на клиенте сведена к минимуму: страница с Fetch API выводит сообщение об ошибке только в консоль браузера, а страница с jQuery такие ошибки не обрабатывает. В частности, ни одна из страниц не сообщает пользователю о том, что токен отсутствует или истек (ответ с кодом 401).
- Схема базы данных топливной базы создается методом `EnsureCreated`, а миграции для нее не применяются, поэтому изменения модели не переносятся в существующий файл базы данных.

Перечисленные ограничения могут служить основой для самостоятельных заданий по доработке проекта.
